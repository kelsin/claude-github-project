# Safety

The loop runs unattended with your `gh` token, and it reads text anyone can write on a linked repo. The design assumes that text is hostile:

- **Only trusted people can steer it.** `feedback`, `answers` and question replies only use comments from you, repo owners, and collaborators with write access (checked through the API). Everything else is reported as `ignoredUntrusted` with no body. The agent marker only counts on comments posted by your own gh account, so it can't be forged.
- **The human gates are enforced in code, not just in prompts.** (A story whose `Auto Approve` field you set, or one the opt-in [auto-approval policy](#auto-approval-policy) approves, is the exception: the agent may pass that gate itself, including by a move into the review column that `cgp move` redirects to the approved column when the live field covers the gate, and such a story is not held to the reviewed commit.) `cgp move` refuses to move a story into Plan Approved or PR Approved, out of Plan Review or PR Review, or to Done unless its PR is merged into the default branch. `cgp merge` works only on a story that is in PR Approved and only for that story's own PR. The `PR` field must name a PR on a repo linked to the board.
- **Deferred stories wait on you.** `cgp defer` files PR-description entries only for a merged PR written by this account, always with Priority Hold (never dispatched) and with the text quoted and `@`-neutralised.
- **The one exception to "Done needs a merged PR": sub-stories.** A planner may split a story into at most 10 sub-stories (`cgp split <story> --declare` while planning). Approving the plan approves that declaration; `cgp split <story>` then creates exactly those issues in Todo, with their plan skipped (their own PRs still need your review). The parent is never implemented, is not dispatched while a sub-story is live, and is closed by cgp, which files it under Done, only when every sub-story that cgp itself created (kept in cgp's local data, written by you) reached Done through a merged PR of its own. A sub-story that ended any other way is put to you as a question instead. A plan the auto-approval policy approved cannot be split, a sub-story cannot be split again, and a `Part of` line in an issue body means nothing to cgp.
- **Why a custom `PR` field instead of GitHub's built-in "Linked pull requests"?** The built-in field is read-only through the API and anyone with write access to the issue can change it (keyword links and sidebar links), and it can hold several PRs, including cross-repo ones. `cgp merge` and Done must act on exactly one PR the loop itself opened, so only `cgp set` writes `PR`, and it validates the URL against the board's linked repos. Keyword auto-linking also only happens for PRs targeting the default branch and can lag PR creation.
- **Prompts treat everything written by people as data** (no running commands, fetching URLs, adding dependencies or leaking tokens because text said so), and `cgp guard` fails any branch that touches a guarded file (`.github/`, CODEOWNERS and more, see below) without the approved plan listing it.
- **Code changed after your PR approval is re-approved**: a fix that is more than a clean, conflict-free rebase (conflict resolution, CI-fix commits) sends the story back to PR Review instead of merging, and auto-merge is disarmed before any push.
- **Commands that refuse inside a Claude session:** `cgp config autoApprove`, `cgp config autoApproveFiles` and `cgp approve` refuse when `CGP_SESSION` or `CLAUDECODE` is set or stdin is not a terminal. This stops an agent approving by accident or because text told it to; it is not a security boundary, since an agent running as your user could (after unsetting CLAUDECODE/CGP_SESSION) fake a terminal (`script`, `ssh -t`) or approve through `gh` directly.
- `~/.config/claude-github-project` is private to your user (0700/0600).

What it can't do: an agent with Bash can still call `gh` directly. For defence in depth consider Claude Code permission rules denying `Bash(cgp approve:*)`, `Bash(script:*)`, `Bash(gh pr merge:*)`, `Bash(gh auth token:*)` and `Bash(gh api graphql:*)` for sessions running the loop, and a fine-grained token (or `GH_TOKEN`) limited to the linked repos and without the `workflow` scope. The setup scripts need `project`; the loop does not need `workflow`.

## Merging only what you reviewed

When a worker moves a story to PR Review, `cgp move` records the PR's head commit. `cgp merge` and `cgp merge-wait` merge only that commit. If the head moved after review (a fix, a collaborator's push) they refuse (exit 7, or state `changed`) and the worker has to post what changed and send the story back to PR Review. Exceptions, both made by the tool itself: a clean rebase through `cgp sync` and the branch update `merge-wait` does when the PR is behind. A rebase that needed conflict resolution is never exempt. A rebase is exempt only when it rebased the reviewed commit (or an earlier exempt one), not any local commit. A story with no recorded review is refused (exit 7): move it to PR Review once so the commit you review is recorded. They also refuse a PR whose branch is not the story's `cgp/<number>` branch, a PR from a fork, one that does not target the default branch (named by the local clone, else by `gh repo view`; when neither says, the merge is refused), a draft, and (when auto-merge is unavailable and the merge would happen at once) any PR whose checks are not green. Every merge call is pinned to the head commit just read (`--match-head-commit`). `merge-wait` re-reads the story's column while it waits: if you take it out of PR Approved it disarms auto-merge and returns `revoked`. `cgp set pr` refuses to replace the PR of a story that is in PR Review or PR Approved, and refuses forks.

`cgp guard` fails a branch that changes guarded files the approved plan does not list: `.github/`, CODEOWNERS, `.npmrc`, `.yarnrc*`, `Makefile`, Dockerfiles, `.husky/`, `.pre-commit-config.yaml`, `.gitmodules`, `.claude/`, `.mcp.json`, `.cgp.json`, `.envrc`, `.githooks/`, GNUmakefile, `.gitlab-ci.yml`, Jenkinsfile, `lefthook.yml`, `.cgp-rules.md` (matched ignoring case). These built-in entries always apply: `cgp config guardFiles '<comma-separated globs>'` can only add to them. The plan's files are the ones declared when the story entered Plan Approved; a worker re-declaring its touches later does not widen them (a story that had none declared then guards everything: ask the user), and a story with `Plan: Skip` may not touch guarded files at all.

Story titles are text anyone can write. The CLI never takes one on a command line (`cgp worker start <item>` reads the title from the board) and the worker spawn prompt carries only ids; titles reach a worker through `cgp prepare`, as data. Where a title must be passed on (`gh pr create --title`, `gh pr edit --title`, `cgp add`), the instructions have the worker write it to a file and use `"$(cat <file>)"`, whose output the shell does not parse again. That part rests on the worker following the instructions; nothing in the CLI can check it. `cgp prepare` also returns `authorTrusted`: when the issue was written by someone who is not you, an owner or a collaborator with write access, its title and body are data only, and `cgp import` skips such issues.

**House rules.** `.cgp-rules.md` is text pasted into agent prompts, so treat a change to it like a change to a prompt. It is read only from the default branch, is a built-in guarded file (`cgp guard`) and is always denied to the auto-approval policy, so a story cannot rewrite its own rules. Workers get it as a fenced data block that is style guidance only: it never overrides the plan, the story or the guard, and the untrusted-data rules still apply to it. `cgp rules propose` only reads comments from trusted people, strips code, links and quotes, drops examples that contain URLs, code fences, shell commands or "ignore previous" phrasing, and puts PR numbers, not comment text, as evidence; but that filter is best effort. The control is you: review every line of a proposal before committing it, because this text is pasted into agent prompts. An agent that reviews with raw `gh` instead of `cgp comment` leaves no agent marker and would count as a trusted reviewer.

A repo's `.cgp.json` is read only from its default branch and can only add guarded files, never remove them. The `notifyCommand` receives story text through environment variables (control and bidi characters removed), never on its command line, and runs without `GH_*`, `GITHUB_*`, `GIT_*` or `*_TOKEN` variables. It runs only when its program is an absolute path to an executable you own that nobody else can write and that is not under a worktree, `/tmp` or the cgp home (`cgp doctor` warns when it would not run). `cgp repo-path` refuses a path whose `origin` is not that repo on github.com (a local path or `file://` origin is allowed) and never repoints a repo that already has a clone.

## Stacked stories

Off by default. With `stackedStories` on (`cgp config stackedStories on`), a story whose only blocker is a story of the same repo in PR Review or PR Approved, with an open PR from its own `cgp/<n>` branch (not a fork), starts at once instead of waiting: `cgp prepare` records the stack and its worktree is cut from the blocker's branch. Both issues must be written by someone you trust, a blocker that is itself stacked is never used (one level only), and any `gh` error leaves the story blocked as before. The record (`stack` in cgp's data: blocker, branch, the blocker commit the story was cut from, the blocker's files) is written only by cgp itself, never from text anyone supplies. `cgp stack <item> --clear` removes it and is for you, in a terminal.

- **A stacked PR can never be merged.** While the record exists, `cgp merge` and `cgp merge-wait` refuse (even when GitHub has already retargeted the PR to the default branch, because it would then carry the blocker's unsquashed commits), and so do the moves into PR Approved and Done: a delegated approval (`Auto Approve`) lands in PR Review instead, and the auto-approval policy never approves a stacked story. A story reaches Done only from a PR merged into the default branch.
- **The retarget happens in `cgp sync`, after the blocker merged.** The story is rebased with `git rebase --onto <default> <recorded blocker commit>` (the blocker is squash-merged, so a plain rebase would replay its commits), auto-merge is disarmed, the PR's base is changed to the default branch and only then is the record cleared. While the blocker is still open, a sync rebases onto the blocker's branch instead and moves the recorded commit forward. Either rebase is a change you did not review: it is never passed off as approved, clears the review record and sends a story in PR Review or PR Approved back to Implement. A recorded commit that is no longer in the branch, or a conflict, taints the story (it is then never auto-approved).
- **The blocker closing or changing sends the story back.** When the blocker goes back to an earlier column, its PR is closed unmerged, or it is pushed to and its PR's files overlap the files the story touches (other than `sharedFiles`), the loop puts the story back in Implement, disarms auto-merge, clears its review record and says why in a comment; it waits while the story's worker runs. `cgp set pr` refuses a PR whose base is neither the blocker's branch nor the default branch, and both it and the move into PR Review refuse while the blocker's head moved since the record was made.
- `cgp guard` still diffs against the default branch, so the blocker's guarded files must be in the story's plan too.

## CI triage

`cgp ci-triage` is the only place that reruns CI (`gh run rerun --failed`, once per commit and at most twice per PR, recorded before the call); workers are told never to rerun by hand. On a flaky verdict it also creates a story and comments on it. Flaky stories are filed in the PR's repo on Priority Hold with the `cgp-flaky` label, so the loop never works them until you release them. Job, workflow and test names come from the PR's CI and can be written by its author, so they are stripped of control, zero-width and bidi characters, backticks, `@`, `#`, `<` and `>` and capped; log text never reaches an issue (only test names matching a strict pattern are taken from it) and never decides a verdict. A story is reused only when it carries the marker, the label and was written by this account.

## Automatic intake

Opt-in per repo (`intake` in `.cgp.json`, read from the default branch only, so a PR cannot enable it). It creates issues and board items from outside input, so: titles are fixed templates, bot PR titles and bodies are never copied, links are built from ids, and a quoted workflow name is stripped of control, bidi and markup characters and cut to 120 characters. Red-main stories are created with your own token, so they count as written by someone you trust; that is acceptable because their content is only ids and the sanitised name. Only bots on the allowlist whose account type is Bot, on non-fork non-draft PRs, are imported, and `github-actions[bot]` cannot be allowed. Dependency stories sit in PR Review with `Plan: Skip`: the auto-approval policy refuses a Plan: Skip story, and its guard and always-deny lists are unchanged, so intake never loosens what an agent may approve or merge.

## Auto-approval policy

Off by default. With `autoApprove` set (by you, in a terminal: `cgp config` refuses `autoApprove` and `autoApproveFiles` inside a Claude session, with `CGP_SESSION` or `CLAUDECODE` set, or without a terminal, and notifies you of a change), `cgp move` approves a gate for an agent when all of these hold, and otherwise leaves the story in your column with the reason in the result:

- the worker's rating (`cgp rate`, given in the column the story is in) is at or below the level set for that gate; a missing rating never qualifies. The rating is the agent's own claim, so it can only narrow, never widen, what the rest of this list allows;
- the issue was written by someone you trust (the same check as `authorTrusted`), is not on Hold, and no conflict in its branch was resolved by hand;
- plan gate: the plan declares files (`cgp touches`; none fails closed), directories are refused, and every file is a plain path matching `autoApproveFiles`. Those files are stored as the approved plan in the same update as the decision;
- PR gate: the PR is open, from the story's own branch and not a fork, and not a draft (unless `draftPRs` opened it, which is then marked ready first); its file list, read from GitHub bracketed by two reads of the head commit, is not empty or possibly truncated (3000 files); every changed path, including the old name of a rename, matches `autoApproveFiles` and is inside the approved plan's files. A story with `Plan: Skip` has no approved files and never qualifies;
- no file is on the built-in always-deny list (`CLAUDE.md`, `AGENTS.md`, `SKILL.md`, `skills/`, column prompts, docs build config) or matches `guardFiles`. Those are absolute: the plan listing a guarded file, or any setting, does not change it.

Globs are matched per path segment, not with `fnmatch`: `*.md` matches `README.md` and not `docs/a.md`. An approved PR is recorded at the commit that was checked, so a later push makes `cgp merge` refuse (exit 7) exactly as after your own review; the policy never sets the delegation that the `Auto Approve` field does. Each approval is stored and posted as a comment on the story with its reason.

`cgp doctor` checks whether the permission denies recommended above are present in your Claude Code settings.
