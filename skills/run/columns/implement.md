# Column: Implement

Implementation and PR review in one run. Stories arrive from Plan Approved (no `pr` link yet), are sent back (the user commented in PR Review) or stalled (a `pr` link exists).

1. Rule 1 (`CGP prepare`), then rate the story (rule 4). `CGP worker phase <item> implementing`. Give implementers and reviewers `houseRules` as rule 4 says.
2. **No `pr` link:** run `CGP overlap` first as in `plan_approved.md` step 2 (when `story.skipPlan` there is no plan to take touches from: declare them with `CGP touches` from your own outline of the change first) (a block recorded here is honored by the loop). Spawn at least one implementer for the plan's step list (1 implementer for a small change), splitting only into disjoint-file parts. Each writes code and tests, runs the repo's own test and lint commands, and commits. Run the full checks yourself in the worktree afterwards. Open the PR per rule 7 (conventional title), with a description that starts with the review packet (rule 7), then a link to the plan (or "Plan: skipped" when `story.skipPlan`), how it was tested, and `Closes <issueRepo>#<number>` (full `owner/repo#n` form when the repos differ), and a `## Deferred` section: one bullet `- <one-line title> :: <one-line reason>` per plan out-of-scope item and per rejected or unfixed reviewer finding (at most 10; leave the section out when there are none). After the merge `CGP defer` files each as a story on hold. Update the PR description (`gh pr edit --body-file`) after fix rounds.
   **Has a `pr` link:** `CGP merge <item> --cancel` (rule 7). `CGP worker phase <item> fixing`. Spawn at least one implementer for the feedback (and `answers`), one per disjoint-file group. Also resolve any CI failure on the PR. Commit and push.
3. Review (CI runs meanwhile). `CGP worker phase <item> reviewing "<n> reviewers"`. Size the change with `gh pr view <pr> -R <repo> --json additions,deletions,changedFiles` and spawn at least one reviewer, more by the rating, each with a distinct lens (correctness, security, tests, simplicity and reuse, performance, compatibility). They read the diff (`gh pr diff`) and the surrounding code and confirm the packet's file list matches the diff, and return concrete findings: severity, file:line, fix. They do not post to GitHub. After a send-back, review only what changed.
4. If any findings were accepted: `CGP worker phase <item> fixing`. Fix every accepted finding at once: at least one fix implementer (several only for disjoint files, in parallel), commit, push after `CGP sync` and `CGP guard`. Rejected findings need a one-line reason in your status comment. High risk only: one more reviewer after the fixes to confirm none remain and nothing new broke. Otherwise skip this step.
5. `CGP worker phase <item> ci`. `CGP ci-wait <repo> <pr> --sha <pushed sha>` and fix until `green` or `none` (max 5 rounds, then ask; on `red` run `CGP ci-triage <repo> <pr>` first and fix only when it says `real`), then `CGP preview <item>`.
6. Reply on the PR to each addressed comment with `CGP comment <item> --pr` (one summary comment is fine, also saying what was reviewed and fixed), then a status comment on the story (PR link, rating, what was tested). Before you finish, finish or `git rebase --abort` any rebase and leave `git status` clean in the worktree (commit intended changes, `git checkout --` files only a test run modified).
7. If `story.autoApprove.pr` is true (the user set Auto Approve to PR or Both), add "auto-approved" to the status comment and `CGP move <item> pr_approved` (the CLI allows it from here only because of that field); the next cycle merges. Otherwise run `CGP rate <item> <low|medium|high>` with your rating (rule 4), then `CGP move <item> pr_review` (the user's PR Review column). That move re-reads Auto Approve live and also asks the user's auto-approval policy (a low-risk change to docs inside the approved plan's files, off unless the user turned it on): if either covers the story, the result has `"autoApproved": true` (and `"requested": "pr_review"`) and the story is in PR Approved; the policy posts its own comment, and you add "auto-approved" to your status comment. Otherwise the story is in PR Review and `policy.reason` (when present) says why the policy refused. If the move is refused with an error, run `CGP move <item> pr_review` and carry on: never retry the policy or lower a rating to get through it.
