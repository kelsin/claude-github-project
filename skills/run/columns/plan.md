# Column: Plan

Planning and plan review in one run. Stories arrive from Todo (no `plan` link yet) or are sent back (the user commented in Plan Review) or stalled (a `plan` link exists).

1. Rule 1 (`CGP prepare`), then rate the story (rule 4). `CGP worker phase <item> planning`. Give planners and reviewers `houseRules` as rule 4 says.
2. **No `plan` link:** explore the code in the worktree `prepare` returned, starting from `brief` when it has one instead of exploring from scratch (a `behind` brief can be out of date: check specifics against the code). Spawn at least one planner (1 for low, more by rating) and merge their drafts into one plan. Put every assumption in the Assumptions section, and every out-of-scope item in the Deferred section as `title :: reason`. Planners must include a Summary graphic in the human part of the plan unless it would add nothing (see `plan_artifact.md`). `CGP touches <item> <paths...>` with the files and directories the plan changes. If the story is too large for one PR, the plan may split it into at most 10 sub-stories: list them in the plan's Sub-stories section and declare them with `CGP split <item> --declare` (JSON list on stdin: `title`, `scope`, `files`, optional `repo` and `after`, a list of titles that must be done first). Declare again after every revision of the plan; an approved declaration is what `CGP split` creates later, so it must match the published plan. Publish the artifact (`plan_artifact.md`) and `CGP set <item> plan <url>`.
   **Has a `plan` link:** collect feedback (`feedback` and `answers` from `prepare`, plus the artifact's comments via ArtifactComments). `CGP worker phase <item> revising`. For each distinct problem or change request spawn at least one agent for the feedback, one per separate section. Questions in comments get answered in the plan or the status comment. Republish, refresh `CGP touches` if the files changed, and reply to each artifact comment you addressed.
3. Review. `CGP worker phase <item> reviewing "<n> reviewers"`. Run `CGP overlap <item>`: if another story changes the same files the plan needs an Ordering note (who goes first, what to rebase on) and must not assume the other story's changes aren't coming. Spawn at least one reviewer, more by the rating, each with a distinct lens: feasibility against the real code, risks and missed edge cases, test strategy, scope creep, security and migrations when risk is high. Give them the overlap result; they read the code through the worktree. Each returns concrete findings: severity, where in the plan, the fix. After a send-back, review only what changed (one reviewer unless risk is high).
4. If any findings were accepted: `CGP worker phase <item> revising`. Spawn at least one agent to apply every accepted finding (one per independent section). Record each finding and its resolution in the Review log; reject a finding only with a reason recorded there. Otherwise skip this step.
5. A finding that needs a decision only the user can make goes in the plan's Open questions and `CGP ask` with your proposed default; then stop without moving.
6. Make sure the published artifact is current, then post a status comment (plan link, rating, key assumptions, review summary and counts).
7. If `story.autoApprove.plan` is true (the user set Auto Approve to Plan or Both), add "auto-approved" to the status comment and `CGP move <item> plan_approved` (the CLI allows it from here only because of that field); the next cycle starts Plan Approved. Otherwise run `CGP rate <item> <low|medium|high>` with your rating (rule 4), then `CGP move <item> plan_review` (the user's Plan Review column). That move re-reads Auto Approve live and also asks the user's auto-approval policy (low-risk docs changes only, off unless the user turned it on): if either covers the story, the result has `"autoApproved": true` (and `"requested": "plan_review"`) and the story is in Plan Approved; the policy posts its own comment, and you add "auto-approved" to your status comment. Otherwise the story is in Plan Review and `policy.reason` (when present) says why the policy refused. If the move is refused with an error, run `CGP move <item> plan_review` and carry on: never retry the policy, change `CGP touches` to fit it, or lower a rating to get through it.
